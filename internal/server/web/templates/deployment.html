Enrollment

agents present this token once, then use their own identity
{{.ServerURL}}
{{.EnrollToken}}
{{.Interval}} seconds
agents replace themselves when this server serves a different build

Agents compare the digest of their own binary with the one this server would send them, so an update happens exactly once and cannot loop. A replacement is downloaded, checksum-verified, and run before it is installed — a binary that cannot execute is discarded rather than bricking the machine. Updates are never offered while a device has work outstanding.

Rotating the token blocks new enrollments with the old value. Devices already enrolled keep working — they authenticate with a per-device token issued at enrollment, not with this one.

Install

one line per platform — the manual steps below it show what that line does

Recommended — one line

curl -fsSL "{{.ServerURL}}/install.sh?token={{.EnrollToken}}" | sudo sh

Detects whether the machine is amd64 or arm64, downloads the matching build, installs to /usr/local/bin, and registers a systemd service. It also clears any retirement marker, so a machine that was previously retired enrols again without further steps. Add --no-service to skip the service, or --prefix DIR to install elsewhere. Pipe to sh -s -- --no-service to pass flags through the pipe.

Manual — 1. download and run

arch=$(uname -m); case $arch in x86_64) arch=amd64 ;; aarch64) arch=arm64 ;; esac
curl -fsSL -o monitorrr-agent "{{.ServerURL}}/download/monitorrr-agent-linux-$arch?token={{.EnrollToken}}"
chmod +x monitorrr-agent
sudo ./monitorrr-agent -server {{.ServerURL}} -enroll-token {{.EnrollToken}} -force-enroll

The uname -m line matters: an Ubuntu VM on an Apple Silicon host is arm64, and running an amd64 binary there fails with cannot execute binary file.

-force-enroll is there so a machine that was retired earlier enrols again rather than exiting. It is on the one-off command only, not the service below: an agent that always forced enrolment would resurrect itself as a new device if it were ever retired and the uninstall failed.

Manual — 2. install as a systemd service

sudo install -m 0755 monitorrr-agent /usr/local/bin/monitorrr-agent
rm -f monitorrr-agent   # the installed copy is the one that matters now

sudo tee /etc/systemd/system/monitorrr-agent.service >/dev/null <<'EOF'
[Unit]
Description=monitorrr agent
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/local/bin/monitorrr-agent -server {{.ServerURL}} -enroll-token {{.EnrollToken}}
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now monitorrr-agent
systemctl status monitorrr-agent

Recommended — one line

curl -fsSL "{{.ServerURL}}/install.sh?token={{.EnrollToken}}" | sudo sh

Same installer as Linux: it picks Apple Silicon or Intel automatically, clears the Gatekeeper quarantine flag, registers a launchd daemon, and clears any retirement marker so a previously retired machine comes back.

Manual — 1. download and run

arch=$(uname -m)  # arm64 on Apple Silicon, x86_64 → amd64 on Intel
[ "$arch" = "x86_64" ] && arch=amd64
curl -fsSL -o monitorrr-agent "{{.ServerURL}}/download/monitorrr-agent-darwin-$arch?token={{.EnrollToken}}"
chmod +x monitorrr-agent
xattr -d com.apple.quarantine monitorrr-agent 2>/dev/null || true
sudo ./monitorrr-agent -server {{.ServerURL}} -enroll-token {{.EnrollToken}} -force-enroll

The xattr line clears Gatekeeper's quarantine flag on an unsigned binary fetched over the network.

-force-enroll is there so a machine that was retired earlier enrols again rather than exiting. It is on the one-off command only, not the daemon below: an agent that always forced enrolment would resurrect itself as a new device if it were ever retired and the uninstall failed.

Manual — 2. install as a launchd daemon

sudo install -m 0755 monitorrr-agent /usr/local/bin/monitorrr-agent
rm -f monitorrr-agent   # the installed copy is the one that matters now

sudo tee /Library/LaunchDaemons/io.monitorrr.agent.plist >/dev/null <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>io.monitorrr.agent</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/monitorrr-agent</string>
    <string>-server</string><string>{{.ServerURL}}</string>
    <string>-enroll-token</string><string>{{.EnrollToken}}</string>
  </array>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
</dict>
</plist>
EOF
sudo launchctl load -w /Library/LaunchDaemons/io.monitorrr.agent.plist

Recommended — one line

irm "{{.ServerURL}}/install.ps1?token={{.EnrollToken}}" | iex

Run it in an elevated PowerShell. It detects whether the machine is amd64 or arm64, downloads the matching build, installs it to C:\Program Files\monitorrr, and registers a scheduled task that runs it as SYSTEM at boot. It also clears any retirement marker, so a machine that was previously retired enrols again without further steps. Installing over a running agent stops the task first, because Windows will not overwrite a running executable.

Passing flags needs the script block form, since a piped script takes no arguments:
& ([scriptblock]::Create((irm "{{.ServerURL}}/install.ps1?token={{.EnrollToken}}"))) -NoService
-NoService skips the scheduled task; -Prefix DIR installs elsewhere.

Manual — 1. download and run

$arch = if ($env:PROCESSOR_ARCHITECTURE -eq "ARM64") { "arm64" } else { "amd64" }
Invoke-WebRequest -UseBasicParsing -Uri "{{.ServerURL}}/download/monitorrr-agent-windows-$arch.exe?token={{.EnrollToken}}" -OutFile "monitorrr-agent.exe"
.\monitorrr-agent.exe -server {{.ServerURL}} -enroll-token {{.EnrollToken}} -force-enroll

This runs the agent from wherever your shell currently is and installs nothing. It is for a quick look: the device appears on the dashboard until you close the window. The $arch line matters on Windows-on-ARM VMs. SmartScreen may warn on an unsigned binary.

-force-enroll is there so a machine that was retired earlier enrols again rather than exiting. It is on the one-off command only, not the scheduled task below: an agent that always forced enrolment would resurrect itself as a new device if it were ever retired and the uninstall failed.

Manual — 2. install as a scheduled task at boot

New-Item -ItemType Directory -Force -Path "C:\Program Files\monitorrr" | Out-Null
Copy-Item .\monitorrr-agent.exe "C:\Program Files\monitorrr\monitorrr-agent.exe" -Force
Remove-Item .\monitorrr-agent.exe   # the installed copy is the one that matters now

$action  = New-ScheduledTaskAction -Execute "C:\Program Files\monitorrr\monitorrr-agent.exe" `
             -Argument '-server {{.ServerURL}} -enroll-token {{.EnrollToken}}'
$triggers = @(
  (New-ScheduledTaskTrigger -AtStartup),
  (New-ScheduledTaskTrigger -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Minutes 1))
)
$principal = New-ScheduledTaskPrincipal -UserId "SYSTEM" -LogonType ServiceAccount -RunLevel Highest
$settings = New-ScheduledTaskSettingsSet -RestartCount 999 -RestartInterval (New-TimeSpan -Minutes 1) `
  -ExecutionTimeLimit ([TimeSpan]::Zero) -MultipleInstances IgnoreNew `
  -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries

Register-ScheduledTask -TaskName "monitorrr-agent" -Action $action -Trigger $triggers `
  -Principal $principal -Settings $settings -Force
Start-ScheduledTask -TaskName "monitorrr-agent"

The install location is not cosmetic: the agent only replaces itself during an auto-update, and only removes its binary on retirement, when it is running from C:\Program Files\monitorrr\monitorrr-agent.exe with the task registered. An agent run from a Downloads folder is treated as someone trying a build by hand, and is left alone.

The second trigger and the zero execution-time limit are both load-bearing. A scheduled task restarts on failure only, but the agent exits cleanly on purpose after replacing its own binary — so without the one-minute repetition an agent that auto-updates never comes back until the machine reboots. And the default three-day execution limit would have Task Scheduler stop a perfectly healthy agent every 72 hours.
